# Два AI-агента и автоматическое улучшение промптов

Решение заданий Lite и PRO занятия 3. Сначала используется Lite: рекрутер оценивает резюме по вакансии, продавец консультирует по учебному курсу «Практика Python». PRO выполняет испытания, предлагает новые промпты и сравнивает версии.

**Текущий статус:** Lite реально испытан через DeepSeek: три рекрутерских случая и три сценария продавца сохранены в `results/lite-deepseek/REPORT.md`. Для длинных многошаговых диалогов `deepseek-v4-pro` оказался надёжнее `deepseek-flash`; локальная проверка схемы включена. PRO-калибровка ещё не выполнена на реальных ответах.

## Подключение OpenAI API

### Подключение через VseLLM

Для выбранного альтернативного провайдера выполните:

```bash
bash scripts/setup_vsellm.sh
```

Мастер принимает новый ключ VseLLM скрытым вводом, сохраняет прежний `.env` в `.env.before-vsellm` (однократно, права 600) и устанавливает `API_BASE_URL=https://api.vsellm.ru/v1`, `API_STYLE=chat_completions`. Рабочая модель и клиент: `openai/gpt-4.1-mini`; судья: `openai/gpt-4.1`. Старый ключ OpenAI не отправляется VseLLM. Сам мастер не выполняет запросы. После ввода ключа запустите `python3 -m lite.preflight`; сервер нужно перезапустить.

Эндпоинт и идентификаторы сверены с [документацией VseLLM](https://vsellm.ru/docs), [карточкой mini](https://vsellm.ru/models/openai/gpt-4.1-mini) и [карточкой GPT-4.1](https://vsellm.ru/models/openai/gpt-4.1). Поддержка строгого `response_format` в просмотренной документации не подтверждена, поэтому исходно установлен `JSON_MODE=prompt`: JSON запрашивается инструкцией и валидируется локально. Доступ к моделям и фактический формат ответа ещё нужно подтвердить короткой проверкой с новым ключом. Запросы и тестовые данные при этом обрабатываются через VseLLM.

### Прямое подключение DeepSeek

Если прокси недоступен, используйте официальный OpenAI-compatible endpoint DeepSeek:

```bash
bash scripts/setup_deepseek.sh
python3 -m lite.preflight
```

Мастер принимает отдельный ключ DeepSeek скрытым вводом и сохраняет резервную копию текущего `.env` в `.env.before-deepseek`. Он настраивает `https://api.deepseek.com`, `deepseek-flash` для рабочих запросов и `deepseek-v4-pro` для судьи. Эти значения соответствуют [официальному примеру API](https://api-docs.deepseek.com/guides/codex) и [описанию Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/). Ключ VseLLM для прямого endpoint DeepSeek не подходит.

### Прямое подключение OpenAI

Для выбранного варианта подготовлен мастер с одним ручным этапом: открыть страницу ключей OpenAI Platform, создать ключ и вставить его скрытым вводом. Ключ сохраняется в `.env` с правами 600; содержимое не выводится. Мастер не отправляет API-запросы и не запускает оплату.

```bash
bash scripts/setup_openai.sh
```

Предустановлены фиксированные версии [GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini) для рабочих агентов и клиента, [GPT-4.1](https://developers.openai.com/api/docs/models/gpt-4.1) для эталонов и судьи. Доступность именно для вашего аккаунта проверяется запросом. Для проверки отправляются всего два коротких запроса:

```bash
python3 -m lite.preflight
```

`.env` автоматически читается приложением; выполнять `source` необязательно. Значения из окружения имеют приоритет. Подписка ChatGPT и использование API оплачиваются отдельно: [официальная информация](https://learn.chatgpt.com/docs/pricing). При ошибке 401 проверьте ключ; при 403 — доступ; при 429 — лимиты и состояние биллинга. Полный прогон запускается отдельно после проверки.

## Запуск Lite

Требуется Python 3.10 или новее. Приложение использует стандартную библиотеку; устанавливать пакеты не нужно.

```bash
cd /home/mike-pi/Documents/coding/NU/Courses/CodexAI-course/Lesson_03
cp .env.example .env
```

В `.env` задайте ключ, адрес API и модели. `WORKER_MODEL` — модель двух агентов; `JUDGE_MODEL` — более сильная модель для эталонов, проверки и улучшения; `CLIENT_MODEL` — модель симулятора клиента (может совпадать с рабочей). Названия моделей и их стоимость определяются провайдером. Мастер задаёт указанные выше модели; в ручной конфигурации их можно изменить.

```bash
set -a
source .env
set +a
python3 -m lite.server
```

Откройте http://127.0.0.1:8765. Для остановки сервера нажмите Ctrl+C. После изменения окружения перезапустите сервер.

Настройки транспорта:

- `API_STYLE=responses` — API Responses, путь `/responses`, структурированный JSON.
- `API_STYLE=chat_completions` — совместимый API, путь `/chat/completions`.
- `JSON_MODE=json_schema` — строгая схема; `json_object` — JSON-режим; `prompt` — схема задаётся только инструкцией. Последние два режима применимы к Chat Completions и требуют поддержки выбранного провайдера. Все ответы дополнительно проверяются локально.

Нативные несовместимые API требуют отдельного адаптера. Ключ хранится только в окружении сервера. В браузер и журнал он не передаётся. В базовом состоянии без ключа можно изучить интерфейс и примеры; модельные ответы недоступны.

### Рекрутер

Вставьте описание вакансии и резюме либо выберите один из трёх примеров. Получите балл 0–100, пять критериев, цитаты, сильные стороны, пробелы и недостающие сведения. Цитаты проверяются на буквальное наличие в резюме; баллы — на сумму и пределы. Если проверка не прошла, интерфейс показывает ошибку, а не достоверную оценку. Модель может ошибаться по смыслу даже при корректном JSON.

Веса: обязательные навыки 40, релевантный опыт 25, результаты 15, дополнительные навыки 10, коммуникации 10. Подробные правила, включая отсутствие данных и отрицания, находятся в `prompts/recruiter_v1.txt`. Итог — рекомендация человеку, не автоматическое решение о найме.

### Продавец

Продукт и условия описаны в `data/product.json`. Чат передаёт модели всю историю текущего диалога, до 21 пользовательской реплики. При обновлении страницы история сбрасывается; сохраните её кнопкой «Скачать диалог». Нет CRM-интеграции: агент предлагает заявку, но не заявляет о фактической отправке.

### Обязательные проверки Lite

```bash
python3 -m lite.check
```

Команда отправляет 12 запросов: три оценки резюме и три диалога по три ответа продавца. В `results/lite-.../` сохраняются фактические ответы и журнал. Ожидаемое поведение всех шести случаев записано в `data/lite_cases.json`. Оценки проходят формальную проверку; смысловые результаты и диалоги нужно сопоставить с ожидаемым поведением. Сам факт завершения команды не означает, что модель прошла все смысловые проверки.

## PRO

Данные уже созданы. Для воспроизведения:

```bash
python3 -m pro.generate
python3 -m pro.run --plan
python3 -m pro.run --smoke --plan
```

`--plan` не обращается к API. Короткий прогон проверяет систему на трёх резюме и трёх сценариях, но не заменяет полное задание.

```bash
python3 -m pro.run --smoke --max-calls 100
python3 -m pro.run --iterations 2 --turns 4 --max-calls 1000
```

Полный план: **782 запроса** без повторных попыток, при двух версиях и четырёх репликах продавца в каждом диалоге. Расходы зависят от провайдера, моделей и длины ответов. Лимит задаёт количество запросов, не денежную сумму. При ошибке выполнение останавливается, уже полученные результаты остаются на диске. Повторный запуск создаёт новый прогон и заново отправляет запросы; автоматического возобновления нет.

### Методика

1. Генератор с фиксированным seed 20261011 создаёт 100 синтетических резюме: сильные, спорные, неполные, противоречивые и с попытками изменить инструкции. Разделение в каждой группе: 12 train, 4 validation, 4 holdout. Итого 60/20/20.
2. Сильная модель создаёт 100 эталонных оценок по фиксированной начальной рубрике. Они сохраняются отдельно. Это модельные эталоны; перед серьёзным применением требуется человеческая проверка.
3. Рабочая модель оценивает train и validation для каждой версии промпта. Сравниваются средняя абсолютная ошибка балла и критериев, совпадение итогового вывода, доля нарушений контракта и неверных цитат.
4. Для продавца подготовлены 30 сценариев трёх типов: интерес, цена, неизвестное условие. Разделение 18/6/6. Модель продавца разговаривает с моделью клиента; сильный судья оценивает весь диалог по пяти критериям 0–2 и отдельно отмечает выдуманные условия.
5. Оптимизатор получает только train: самые существенные расхождения рекрутера и слабые диалоги продавца. Он объясняет типичные ошибки, предлагает изменения и сохраняет новый полный промпт. Validation и holdout в запрос оптимизатора не попадают.
6. По validation выбирается лучшая версия каждого агента. Для рекрутера сначала минимизируется доля формальных ошибок, затем ошибка балла, затем максимизируется совпадение вывода. Для продавца сначала минимизируется доля диалогов с выдумками, затем максимизируется средняя оценка. При равенстве сохраняется ранняя версия.
7. После выбора первая и последняя версии проверяются на одинаковых holdout-резюме и сценариях. Промпты после этого не обновляются. Итоговый отчёт показывает изменения метрик и оставшиеся ошибки. Улучшение не гарантируется и не подставляется заранее.

Для продавца одинаковы персоны и первые реплики, но продолжения генерируются заново в ответ на продавца. Это сравнение на одинаковых сценариях, а не на одинаковом тексте диалогов. Один стохастический прогон не доказывает статистическую значимость. Если лучшей стала промежуточная версия при числе итераций более двух, она выбрана по validation; holdout-сравнение всё равно относится к первой и последней версиям по условию задания.

### Что сохраняется

В каждой папке `results/pro-.../`:

- `manifest.json` — параметры, модели, статус, плановое и фактическое число запросов, хеши данных;
- `datasets/` — снимок входных данных; `references/` — эталонные оценки;
- `prompts/` — полные версии; `changes/` — причины и содержание изменений;
- `evaluations/` — ответы, диалоги, оценки по каждой итерации и выборке;
- `selection.json`, `summary.json`, `REPORT.md` — выбор версии, метрики и итоговое сравнение;
- `calls.jsonl` — фактические запросы, ответы провайдера, token usage при наличии, длительность и ошибки. Тексты резюме и диалогов входят в журнал.

## Проверка кода

```bash
python3 -m unittest discover -s tests -v
node --check static/app.js
```

Тесты проверяют разделение данных, контракты ответов, цитаты, пороги, транспорт, отсутствие ключа в журнале, полный цикл PRO с заглушкой и сохранение при сбое. Временные фиктивные результаты удаляются автоматически и не включаются в реальные отчёты.

## Сдача

После реального прогона проверены результаты Lite, затем подготовлен отчёт PRO. По условиям задания нужен общий доступ к чату либо экспорт чата на Диск. Ссылка на чат создана через меню «Поделиться» после завершения испытаний. 

## Источник API-контракта
